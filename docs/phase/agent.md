### 重点要求

1. 不要硬编码,将外部注入类型的数据建立在外部
2. llm的输入输出一定要精确且简短
3. agent的修改需要同时修改提示词,代码,输出Json,配置信息集成在外部
4. 对于所有测试需要使用真实LLM完成
5. 规范(draft_spec)优先
6. 完成任务后产出汇报文档到donlist中
7. 每个函数和对象必须提供中文注释
8. 所有实现必须要保障响应智能与可落地性；当前默认导向优先服务历史/文学教育型互动，而不是单纯追求跑团式刺激体验,
9. model文件夹中的数据模型是和规划文档同等级别的需求,必须被强制消费,禁止在其它代码文件夹中实现相同含义的数据模型,且必须围绕此数据模型进行工作,不得在有需要的情况下绕过

### 其它问题
1. 环境统一策略
- 真实联调统一使用一个解释器（优先conda），固定命令前缀执行。
- 启动脚本前显式设置PYTHONPATH=.
- 将依赖安装命令和运行命令写入donelist，避免口头约定。

2. 可观测性与证据沉淀
- 三条真实用例必须输出终端过程，并同时落盘log与json。


3. 配置到请求体闭环
- 配置新增llm.enable_reasoning后，请求体同步传递关闭推理参数，确保配置项真实生效。
- 对不支持结构化输出的提供方保留降级路径，保证链路可用性。

4. 变更同步机制
- 每次agent相关改动，按提示词->模型->代码->配置->测试报告的顺序检查一遍。
- 发现字段契约变化时，先改数据模型再改提示词和调用方，最后回归测试。

5. LLM测试流程约束
- 需要真实LLM调用的测试
- 测试完成后立即写入phase对应donelist，记录输入、过程、结果、失败原因与修复动作。

### 下一轮迭代建议
1. 变更入口顺序
- agent相关字段或输出结构一旦变化，先检查 `src/data/model` 是否已有真值定义。
- 如果 model 已定义，业务代码必须直接消费，不允许在 agent、engine、rule 内再定义同义结构。
- 推荐检查顺序固定为：`draft_spec/model -> prompt -> llm/output model -> engine/rule 调用方 -> tests -> donelist`。

2. 鉴定链路实现约束
- 凡是实现了“鉴定”而不是空实现，至少要区分 `num` 与 `against` 两类链路，不能把对抗鉴定偷折叠成单人数值检定。
- 对抗鉴定除结果文本外，还要保证参与方、胜者、受影响对象这些结构化信息能继续向下游传递。
- `num` 与 `against` 的输入校验不能混写，避免把单人鉴定错误地要求成必须带对抗对象。

3. 状态写入运行时约束
- `extensions.*` 是否可写，不能只停留在 model 声明层，运行时 patch 也必须检查 `extension_registry`、`mutable` 和基础类型。
- 如果本轮只做了最小运行时校验，要在 donelist 或报告里明确当前边界，避免后续误判成“已完整收口”。

4. 提示词与实现对齐约束
- prompt 中写出的字段语义、数量约束、ID 约束，必须在代码层有对应校验，不能只依赖模型“听话”。
- 如果 prompt 新增了结构化字段，测试至少补一条成功样例和一条非法样例，证明校验与降级策略真实生效。

5. 测试与证据策略
- 真实 LLM 联调前先确认 key、窗口和解释器环境，避免把环境问题误判成实现问题。
