# 审查结论

- 当前审查范围：`phase1 -> phase3`
- 当前总体进度：进行中
- 主要风险：Phase1-3 主链已经能跑，但仍存在 `engine.py` 结构重复、model 真值未被完整消费、以及 phase3 状态链细节未收口的问题
- 是否满足当前阶段目标：部分满足

## 说明

- 本次 review 只覆盖 `phase1 -> phase3`。
- `phase4 -> phase7` 属于后续阶段内容，本轮不将其“尚未实现”记为问题。
- `src/data/model` 视为项目唯一真值来源；本轮重点看的是 model 外代码是否真正消费了它，而不是要求删减 model 本身。

## 问题清单

### 一类：当前代码结构问题

#### 1. 高：`engine.py` 以双类继承维护 phase2 / phase3，公共链路重复实现，结构不够优雅

- 问题是什么：
  `Phase2Engine` 和 `Phase3Engine` 共享大量相同逻辑，但通过继承复制了输入分流、DM 处理、E1/E3/E7 组装、Evolution 前置构建等流程。
- 为什么是问题：
  phase3 只是 phase2 的扩展分叉，不应通过两套公开类并行维护。当前结构会放大后续修改成本，也更容易让 phase2/3 行为慢慢漂移。
- 影响范围：
  `engine.py` 可维护性、测试迁移成本、phase2/3 行为一致性。
- 相关文件或证据：
  - `src/engine/engine.py`
- 建议修复方式：
  收敛为单一 `Engine`，通过 `mode` 控制 phase2 / phase3 分流；公共步骤只保留一份私有实现。

#### 2. 高：规则结算结果存在 model 外重复定义，未强制消费 model 真值

- 问题是什么：
  `rule_system.py` 自己定义了 `CocCheckResult`，而不是直接使用 `src/data/model` 内的结构化模型。
- 为什么是问题：
  这正是“model 已定义语义，业务代码却在 model 外再写一份同义结构”的典型问题。继续这样做会让 model 失去唯一真值地位。
- 影响范围：
  `rule_system`、`engine`、tests 的结果对象来源一致性。
- 相关文件或证据：
  - `src/rule/rule_system.py`
  - `src/data/model`
- 建议修复方式：
  把规则结算结果迁回 `src/data/model`，`rule_system` 与 `engine` 只消费 model，不再保留本地同义定义。

#### 3. 中：部分调用方对同一结果结构存在多种读取方式，说明接口组织还不够稳定

- 问题是什么：
  现有 phase2 代码和脚本对 `dm` 结果有两种读取路径：有的按扁平字段读，有的按 `llm_output.intent_info` 读。
- 为什么是问题：
  这反映出上层返回结构虽然能用，但表达不够稳定，调用方已经开始形成各自习惯。
- 影响范围：
  phase2 脚本、测试、后续联调代码。
- 相关文件或证据：
  - `tests/phase2/test_phase2_serial_pipeline.py`
  - `tests/phase2/run_real_cases_local.py`
  - `tests/phase2/generate_routing_samples.py`
- 建议修复方式：
  在不改变 model 语义的前提下，统一 engine 对外返回组织；至少确保调用方不需要猜测读取路径。

### 二类：Phase1-3 范围内仍存在的实现缺口或保守风险

#### 4. 中：DSL 已完成基础落地，但字段权限约束仍偏弱

- 问题是什么：
  当前 `DslEngine` 能解析和访问 snapshot 中存在的字段路径，但没有体现“受约束字段路径”的更细权限控制。
- 为什么是问题：
  从 phase1 验收角度它已经完成了“可解析、可求值”，但从规范收口角度看，还缺少更强的字段授权边界。
- 影响范围：
  `ASSERT`、条件判断、后续复杂 DSL 扩展。
- 相关文件或证据：
  - `src/rule/dsl.py`
- 建议修复方式：
  本轮在 review 中明确其为“phase1 已完成、但仍有约束细化空间”，不在本次代码改动里改变 DSL 语义。

#### 5. 中：鉴定链路仍是简化实现，`against` 语义没有完全闭环

- 问题是什么：
  `_run_check` 只取第一个属性做单次鉴定，`against_char_id` 没有进入真正的对抗结算。
- 为什么是问题：
  这属于 phase2/3 范围内的实现简化，不应被误判为 phase4 之后的问题，但也确实会限制复杂交互表达。
- 影响范围：
  `engine`、`rule_system`、Evolution 输入真实性。
- 相关文件或证据：
  - `src/engine/engine.py`
  - `src/rule/rule_system.py`
- 建议修复方式：
  本轮优先统一规则结果的 model 真值来源；复杂对抗鉴定保持为已知简化项，在 review 中明确记录。

#### 6. 中：Phase3 的状态链已有重试/回滚，但观测字段仍有收口空间

- 问题是什么：
  状态分支已经具备自动重试、错误反馈和回滚，但错误历史与计数字段仍偏“够用”，不够清晰。
- 为什么是问题：
  这不会阻断 phase3 主链，但会影响排障和后续 done 物料质量。
- 影响范围：
  `_run_state_branch`、回滚日志、问题定位效率。
- 相关文件或证据：
  - `src/engine/engine.py`
- 建议修复方式：
  保持现有 phase3 行为不变的前提下，后续可继续细化重试次数、尝试次数和超时退出的记录。

#### 7. 中：物品位置唯一真值与背包表现之间仍有设计张力

- 问题是什么：
  规范强调 `location` 是唯一真值，但当前角色上仍保留 `inventory`，而 `\inventory` 元命令直接读取该字段。
- 为什么是问题：
  在不改 model 语义的前提下，这一设计暂时可以工作，但它确实要求后续代码非常克制，不能再引入更多“第二套位置真值”。
- 影响范围：
  元命令显示、状态补丁、物品移动链路。
- 相关文件或证据：
  - `src/data/model/base.py`
  - `src/rule/rule_system.py`
  - `src/rule/state_patch.py`
- 建议修复方式：
  本轮不改 model 含义，只在代码层避免继续扩散第二套真值，并在 review 中把它明确为 phase3 内尚需收口的设计张力。
