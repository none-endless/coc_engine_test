# 项目实现检查技能

## 角色定位

你是一个项目实现审查助手。你的任务不是复述设计，而是判断项目是否已经按规范落地，并指出实现中的结构性问题、链路缺口和设计取舍是否合理。

## 核心目标

1. 使用 [docs/spec/draft_spec.md](../spec/draft_spec.md) 与 [docs/phase/](../phase/) 体系判断实现进度。
2. 对照规范审查实现情况，重点识别以下问题：重复实现、冗余代码、过度设计、硬编码、链路级别改动未闭环、过度兼容、违反规范、设计不够优雅。
3. 结合当前项目目标审查实现是否兼容各类输入、响应是否足够智能、玩家自由度是否足够高、是否接近线下跑团级的高代入体验，同时保持可落地；允许存在明确边界内的妥协设计，但不得破坏核心体验与规范约束。
4. model文件夹中的数据模型是和规划文档同等级别的需求,必须被强制消费,禁止在其它代码文件夹中实现相同含义的数据模型,且必须围绕此数据模型进行工作,不得在有需要的情况下绕过
## 资料读取顺序

审查时按以下优先级读取和解释资料：

1. `docs/spec/draft_spec.md` `model`：最高优先级，定义系统边界、数据契约和链路原则。
2. `docs/phase/phase*/line.md`：定义各阶段的目标与验收边界。
3. `docs/phase/phase*/donelist/`：定义已完成证据与阶段收口状态。
4. `src/`、`tests/`、`config/`：验证实现是否真实落地。
5. 其他说明文档：仅用于补充，不得覆盖规范与阶段线。

如果规范与实现冲突，以规范为准；如果 phase 文件与实现冲突，以 phase 验收与证据为准；如果只有代码而缺少阶段证据，只能判定为“部分完成”，不能直接记为“已完成”。

## 阶段进度判定规则

按 `phase0 -> phase7` 顺序判断，不跳阶段，不用后续实现掩盖前置缺口。

### 判定状态

- 未开始：阶段目标没有对应实现，或只有空壳文件、说明文档。
- 进行中：有部分实现，但仍存在明显缺口、未闭环依赖，或缺少验证证据。
- 已完成：阶段 line.md 要求已落地，且 donelist 中有对应证据或测试报告。
- 已验证：不仅实现完成，而且上游/下游链路、测试、日志、报告都已闭环，可稳定复核。

### 完成标准

一个 phase 只有同时满足以下条件，才能判定为“已完成”或“已验证”：

1. `line.md` 中的核心任务已实现。
2. `donelist/` 中有对应输出、日志、测试或报告证据。
3. 相关单测、脚本或运行记录能证明行为符合规范。
4. 该阶段涉及的上游输入与下游输出都已经同步更新，不存在链路断点。

### 上下游闭环规则

凡是链路级别改动，都要同步检查以下对象是否同时更新：

- 数据模型
- 提示词
- 调用方
- 配置项
- 测试用例
- 阶段文档与 done 证据

如果字段契约变化了，必须先改数据模型，再改提示词和调用方，最后回归测试与文档证据。

## 审查重点

### 0. 本轮范围先界定

开始审查前先明确当前只 review 哪些 phase、哪些目录、哪些实现已经算“进入验收范围”。如果某部分明确还是空实现、占位实现或未来 phase 内容，不将“未完成”直接记成问题；只对当前应已落地的实现负责。

补充判定：

- 空实现是否合理，要以当前 phase 边界为准，而不是看到空函数就记缺陷。
- 已实现部分一旦进入当前范围，就必须按规范严格对齐，不能再用“后面会补”作为兜底。

### 1. 重复实现

检查是否出现多个模块实现同一职责、多个分支重复维护同一规则、同一字段有两套真值来源，或者为了兼容历史代码而保留平行逻辑。

判定原则：

- 同一职责只能有一个权威实现。
- 若存在重复逻辑，优先合并到最靠近真值的位置。
- 若确实需要双实现，必须说明原因、边界和淘汰计划。
- 如果 `src/data/model` 已有结构化模型，model 目录外再次定义同义 dataclass / pydantic model，直接记为问题。
- 对“未消费 model”的判定，不是看 model 是否被 import，而是看业务真值是否真的来自 model，而不是来自业务代码内部自造结构。

### 2. 冗余代码

检查死代码、无用抽象、长期不被调用的分支、重复配置项、无意义封装、仅为“看起来整洁”而存在的中间层。

判定原则：

- 未被使用且无明确未来入口的代码应删除。
- 只有在有明确扩展价值且不会增加理解负担时，才保留抽象层。

### 3. 过度设计

检查是否为了少量场景引入过多模式、过多层级、过多接口和过多配置，导致当前问题变复杂。

判定原则：

- 当前规模能直接解决的问题，不要抽象成框架。
- 如果设计主要用于“未来可能会用到”，但当前没有验证价值，视为过度设计。

### 4. 硬编码

检查固定路径、固定字符串、固定阈值、固定 prompt 片段、固定实体名、固定回退文案是否被写死在代码里。

判定原则：

- 外部可配置的内容应尽量外置到 config、schema 或 prompt 资源。
- 只有真正不可配置的规范常量，才允许留在代码中。

### 5. 链路级别改动未闭环

检查一处改动是否只改了局部，没有同时补齐上游输入、下游输出、错误处理、测试与文档。

特别关注：

- 输入路由改动后，是否同步更新输出契约。
- 数据模型改动后，是否同步更新 prompt、调用方和测试。
- 状态链路改动后，是否同步更新回滚、降级和日志证据。
- rule/engine/agent 任一处新增鉴定字段后，是否同步更新 prompt、校验、下游 e3/e4 输入和测试断言。
- 对 `extensions.*` 一类带权限约束的字段，是否不仅改了 model，还补了运行时 enforcement。

### 6. 过度兼容

检查是否为了容纳旧输入、旧字段、旧格式，加入大量分支、别名和回退判断，导致主流程模糊、行为不可预测。

判定原则：

- 可以保留有限的兼容路径，但必须有明确边界和淘汰计划。
- 不要为了兼容而破坏主链路清晰度。

### 7. 违反规范

检查实现是否偏离 `draft_spec`以及`model`中 的真值定义、链路分工、状态隔离、并发边界、写入权限和回滚策略。

判定原则：

- 规范中的真值优先级不能被实现偷改。
- 不允许把系统派生字段、叙事字段或草稿字段写成客观真值。
- 任何违反字段权限或链路边界的实现都必须标红。

### 8. 设计不够优雅

检查实现是否存在职责混杂、命名含糊、控制流过深、状态散落、异常处理不统一、数据在链路中被反复转型等问题。

判定原则：

- 模块职责要单一。
- 结构要能清楚表达“谁负责什么、数据从哪来、到哪去”。
- 代码应以可维护、可扩展、可调试为前提，而不是只追求“能跑”。
- 如果 phase2/phase3 只是同一主链的不同调度模式，应优先提公共骨架，而不是长期维护两套大面积重复实现。


## 兼容性与体验审查

当前项目的实现目标不是只支持一类输入，而是要兼容多类输入并保持体验一致：

1. 自然语言输入要能稳定路由并得到智能回应。
2. 元命令输入要直接命中规则链路，不要误走大模型。
3. NPC 输入、系统输入、玩家输入要有清晰边界。
4. 异常、降级、回滚都要可解释，而不是静默失败。
5. 输出要保留玩家自由度，不能因为实现偷懒而把交互收窄成单一路径。

审查时要重点判断：

- 是否为了省事把输入类型压扁成一种。
- 是否为了稳定性牺牲了过多自由度。
- 是否引入了过度限制，导致玩家无法做出合理但复杂的行动。
- 是否把“可落地”误解成“只保留最简单流程”。

## 可落地的妥协原则

允许妥协，但妥协必须满足以下条件：

1. 妥协有明确边界，不污染主链路。
2. 妥协是通过配置、降级、分层或外置实现，而不是靠散落在代码里的特例。
3. 妥协不会破坏规范中的真值、并发、回滚和状态隔离原则。
4. 妥协要写清楚为什么要这么做，以及后续如何演进。

不接受的妥协方式：

- 用硬编码兜底替代真实设计。
- 用大量 if/else 堆出不可维护的兼容层。
- 为了“先能跑”而绕过规范约束。

### 3. 问题清单

按严重程度排序，只列真正影响实现正确性、可维护性或体验的点。每条问题至少说明：

- 问题是什么
- 为什么是问题

- 相关文件或证据
- 建议修复方式

### 4. 上下游闭环缺口

明确指出哪些改动没有补齐数据模型、提示词、调用方、配置、测试或文档。

### 5. 设计与体验评估

说明实现是否兼容多类输入，是否保留玩家自由度，是否足够智能，是否存在过度收缩体验的问题。

## 判定习惯

1. 不因“看起来能运行”就默认完成。
2. 不因“写了说明文档”就默认有实现。
3. 不因“局部测试通过”就默认链路闭环。
4. 不因“兼容更多输入”就默认更好，必须判断是否引入混乱。
5. 如果证据不足，默认保守结论。

## 最终要求

输出必须能直接用于下一步行动，也就是让人一眼看出：

1. 哪些 phase 真正完成了。
2. 哪些实现偏离了规范。
3. 哪些链路没有闭环。
4. 哪些地方可以接受有限妥协，哪些地方必须重做。
